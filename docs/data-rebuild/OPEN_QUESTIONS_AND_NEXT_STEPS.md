## 1. Unresolved questions

Five of these were discovered by profiling, not anticipated. Three change the
architecture rather than a parameter. Each is registered in
`data/source_registry/source_registry.yaml` under `unresolved:`.

### Q1 — IBM has almost no individual behavior `UNRESOLVED_INDIVIDUAL_BEHAVIOR`

**Blocks Phase 3, Phase 9. Highest impact.**

IBM's 2,077,023 accounts break down as 35% Partnership, 33% Corporation, 32%
Sole Proprietorship, and **0.15% Individual — 3,017 accounts**. Of those, only a
few hundred have 10 or more transactions.

The rebuild's premise is that IBM supplies behavioral backbone for synthetic
Vietnamese KYC agents. For businesses that works well. For individuals — which
is most of a retail bank's customer base and most of what Hường will model —
IBM has essentially nothing to supply.

| Option | What it costs |
|---|---|
| **A. Business-led release.** Model the bank as SME/corporate-focused. Individuals appear only as a small segment matched to the 3,017 individual accounts. | Honest, uses IBM as-is, needs no invention. But it is not the retail AML dataset the project set out to build, and Hường's retail behavioral features get a small population. |
| **B. Hybrid.** Businesses matched to IBM; individuals generated by a Vietnamese retail behavioral model with IBM supplying only network topology. | Gets a realistic retail population. Costs a second generation path, and individual behavior is then parameter-driven — the thing the rebuild was meant to move away from. |
| **C. Re-label.** Treat Sole Proprietorships as individual-like. | Cheap and wrong. A sole proprietorship's cash flow is a business's, and calling it retail would misrepresent the dataset to both consumers. |

**Recommendation: B**, with the individual behavioral model documented as
parameter-driven and explicitly listed in `manifest.json` under
`known_limitations`. A is defensible if the project accepts an SME-focused
scope; C is not defensible.

### Q2 — the observation window is 27.67 days `UNRESOLVED_OBSERVATION_WINDOW`

**Blocks Phase 11, Phase 16.**

2022-09-01 to 2022-09-28. The previous design assumed ~90 days, and both the
split policy and the rolling-window feature set were built on that.

| Option | What it costs |
|---|---|
| **A. Accept 28 days.** Drop the chronological split; split by entity and network only. | Loses monthly seasonality, 30/60/90-day baselines, and time-based leakage protection. |
| **B. Tile the window.** Concatenate the 28 days three times with distinct entities per tile. | Gives 84 days, but each entity still only lives 28 days, so long-horizon features stay empty. Mostly cosmetic. |
| **C. Use a larger IBM file.** `HI-Large_Trans.csv` is ~180M rows — but the window is a property of the simulator, not the file size. |Needs verification; the large files likely span a similar period. |

**Recommendation: A** for v0.1.0, with the window recorded as a known limitation
and Hường's feature set scoped to windows of 14 days or less. Verify C before
committing, since it costs one profiling run to check.

### Q3 — payment format leaks the label `UNRESOLVED_PAYMENT_FORMAT_LEAKAGE`

**Blocks Phase 11, Phase 12, Phase 14.**

87.3% of laundering rows are ACH against a 12.1% baseline (7.2× lift), and Wire
and Reinvestment contain zero laundering rows in 3.07 million transactions.

| Option | What it costs |
|---|---|
| **A. Re-map through a Vietnamese channel model** independent of the label, using SBV channel shares. | Removes the leak, fixes the implausible 38% Cheque share, gives a Vietnamese taxonomy. Loses IBM's format-behavior correlation. |
| **B. Drop the column.** | Simple, but discards a feature real AML models use. |
| **C. Keep it.** | Fails Phase 14 on arrival. Not viable. |

**Recommendation: A.** It solves the leak and the realism problem in one step.
The channel assignment must be conditioned on customer archetype and amount —
never on the label — and Phase 14's leakage test must run against the result.

### Q4 — timestamps carry no daily rhythm `UNRESOLVED_TEMPORAL_REALISM`

**Blocks Phase 11, Phase 12.**

Every hour from 01:00 to 23:00 holds 3.88–3.90% of transactions. IBM assigns
times uniformly at random.

| Option | What it costs |
|---|---|
| **A. Re-draw the time-of-day** through a Vietnamese diurnal model, preserving date and event ordering. | Restores night/business-hours features. Changes intra-day inter-arrival structure, which IBM did not really have anyway. |
| **B. Keep IBM timestamps** and declare temporal features unsupported. | Preserves the source exactly; costs Hường a standard feature family. |

**Recommendation: A**, restricted to time-of-day within the existing date, so
transaction ordering and the daily network structure are untouched.

### Q5 — no source links income to account turnover `UNRESOLVED_INCOME_TO_TURNOVER`

**Blocks Phase 8.**

Phase 8 maps IBM behavioral ratios onto a customer's expected income or revenue.
No registered source states what multiple of monthly income passes through a
Vietnamese bank account. GSO gives income; SBV gives system-wide payment totals;
neither gives the ratio.

**Recommendation:** register it as an explicit assumption parameter with a wide
sensitivity range, flagged `confidence: low`, and generate the small release at
three settings so the sensitivity is measured rather than asserted. Do not
present a single derived number as evidence-based.

### Q6 — accounts per customer is unevidenced `UNRESOLVED_ACCOUNTS_PER_CUSTOMER`

**Blocks Phase 10.** Lower impact.

Findex gives account ownership rates, not accounts held at one bank. IBM's
accounts file gives accounts per entity, but for a foreign business population.

**Recommendation:** start with one account per individual and allow multiple for
businesses using IBM's observed entity-to-account distribution, since businesses
are the population IBM actually represents. Register as an assumption.

### Q7 — clustering dependencies are not installed

**Blocks Phase 3.** Mechanical, but must be decided before Phase 3 starts.

The environment has `pyarrow` and `PyYAML` only. K-means, GMM, and silhouette
scoring need `numpy` and `scikit-learn`.

**Recommendation:** add `numpy` and `scikit-learn` to `requirements-dev.txt`
rather than `requirements.txt`. Archetype derivation is an offline analysis step,
not something the API/worker image should carry.
