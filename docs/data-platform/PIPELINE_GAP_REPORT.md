## Positive controls already present

These are not gaps and should be preserved:

- Producer uses `acks=all`, idempotence, high retry allowance, bounded in-memory queueing, delivery callbacks, and a final flush.
- Raw events use a stable deterministic `transaction_id` and a stable sender-account Kafka key.
- Topic names, group ID, offset reset, HDFS base path, format, parallelism, and checkpoint interval are configurable with stable defaults.
- Kafka, producer checkpoint/error logs, HDFS namespace/data, and Flink checkpoint files use persistent named volumes/HDFS paths in the local Compose project.
- Malformed Kafka events are routed to HDFS rejected output instead of crashing or being silently dropped.
- Producer-side malformed CSV rows go to both a Kafka DLQ and local fallback file.
- Event time and UTC HDFS partition derivation are explicit; idle partitions are accounted for.
- The FileSink uses checkpoint-coordinated file completion; consumers can avoid in-progress files.
- Existing synthetic fixture generation uses a fixed seed, and the committed fixture contains no claimed production credentials.
- Python unit tests cover checkpoint tracking, schema, parsing, deterministic IDs, replay selection, and malformed rows; Java tests cover parsing, validation, partition paths, split routing, and sink construction.
- Root `.env`, data, logs, Python environments, Node dependencies, Java build output, and common IDE files are already ignored.

## Delivery guarantee conclusion at this phase

The complete path must currently be treated as **at-least-once**:

- librdkafka idempotence protects retry duplicates within a producer session, but the CSV resume checkpoint can resend acknowledged rows after a crash window;
- Flink checkpointing coordinates Kafka source state and FileSink state during supported task recovery, but restart/savepoint behavior has not been proven at this commit;
- HDFS bronze has no deduplication and deliberate replay is append-only.

The repository may accurately say that completed FileSink files are checkpoint-committed and readers should not see partial files. It must not describe the complete producer-to-bronze pipeline as exactly-once until restart and replay evidence proves every boundary and duplicate count.

This initial report classifies gaps. Apart from the credential removal and obsolete CI assertion, no pipeline hardening should be applied until Bảo reviews priorities and a Docker-capable test environment is available.
